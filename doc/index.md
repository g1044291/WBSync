# WBSync 設計ドキュメント

工数（人日）ベースでスケジュールを自動生成するWBSデスクトップアプリ。単一ユーザー、Windows専用、〜100タスク規模を前提とした軽量ツール。

## 設計思想

本ドキュメント群は Google の [Open Knowledge Format (OKF)](https://cloud.google.com/blog/ja/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing/) を参考に構成している。

OKFが解決しようとしているのは「ナレッジの断片化」問題である。仕様がWiki・コードコメント・巨大な単一ドキュメントなどに散在していると、変更のたびに関連箇所を探し出す・整合を取るコストが高くつく。OKFはこれを「YAMLフロントマター付きMarkdownファイルの集合＋相互リンク」という最小限の形式で解決する。SDKや専用ツールを必要とせず、人間にもAIエージェントにもそのまま読み書きできる点が要である。

WBSync のようにドキュメント自体は小規模でも、以下の理由から本形式を採用する価値があると判断した。

* **変更の波及を追いやすい** — テーブル・画面・要件が1トピック1ファイルで分かれ、相互リンクを持つため、「このテーブルを変えたらどの画面・要件に影響するか」を辿れる（旧来の3巨大ファイル構成では、変更のたびに数百行のファイル全体を読み返す必要があった）。
* **AIエージェントによる保守と相性が良い** — Claude Code のようなエージェントがコード変更に合わせてドキュメントを更新する際、変更対象のファイルだけを読み書きすればよく、無関係な記述を巻き込まない。
* **プラットフォーム非依存** — 特定のWikiツールやドキュメント生成SDKに依存せず、Gitリポジトリ内のMarkdownとして完結する（ポータビリティを優先するWBSync自体の設計方針とも一致する）。

OKFが定める3原則をこのリポジトリでは次のように適用している。

| OKFの原則 | このリポジトリでの適用 |
|---|---|
| 制限が最小限（必須は `type` のみ） | フロントマターは `type` / `title` / `description` / `tags`（＋任意で実装ファイルへの `resource`）に統一。本文構成は各ファイルの内容に委ねる |
| プロデューサー/コンシューマーの独立性 | 人間（設計者）が編集し、AIエージェント（Claude Code）が実装時に参照・更新する、という双方から扱える形式にする |
| プラットフォームではなく形式 | 特定のツール・SDKを介さず、Markdown＋Gitのみで完結させる |

なお、OKFはメタデータカタログ（BigQueryテーブル等）とAIエージェントの橋渡しを主眼としているのに対し、WBSyncでは「要件・DB・UIという3つの関心事の間を人間・エージェントの双方が行き来しやすくする」ことを目的に応用している。

## 構成

| ディレクトリ | 内容 |
|------|------|
| [requirements/](requirements/index.md) | 機能要件・非機能要件 |
| [tables/](tables/index.md) | DBテーブル定義・ER図（DDL・インデックスは各テーブルファイルに記載） |
| [screens/](screens/index.md) | 画面レイアウト・画面遷移・共通ルール |

## 読み方

* 各ディレクトリの `index.md` が一覧・概要（＋横断的なER図など）を持ち、個別のコンセプト（要件項目・テーブル・画面）は1ファイル1トピックで存在する。
* 各ファイルはYAMLフロントマター（`type` / `title` / `description` / `tags`、必要に応じ実装ファイルへの `resource`）を持つ。`timestamp` など更新の度に手で保守する必要があるだけで実利のないフィールドは持たない（更新日時が知りたければ `git log` を見ればよい）。
* 本文中のMarkdownリンクで関連トピック（テーブル ↔ 画面 ↔ 要件）を相互参照する。ただし WBSync は要件同士・画面遷移が密に結合した小規模アプリのため、リンクを再帰的に辿ると最終的にほぼ全ファイルへ到達する。**「関連」リンクは目的地を探すための地図であり、辿れるからといって全部読む必要はない。** 特定機能の改修を頼まれたら、まずその機能に直接対応する requirement / table / screen だけを読み、必要になった時だけ関連リンク先を開くこと。
* 画面ファイル名・見出しに `S01` のような画面IDは付与しない（人間にもAIエージェントにも識別子としての価値がなく、コードにも持ち込まない方針のため）。画面名がそのままファイル名・見出しになる（例: `screens/gantt-chart.md`）。

## 更新ルール

機能追加・仕様変更を行った際は、関連するドキュメントを都度更新すること（要件変更時は `requirements/`、画面変更時は `screens/`、テーブル変更時は `tables/`）。
