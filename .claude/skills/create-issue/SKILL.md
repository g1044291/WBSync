# Issue作成

ユーザーの要望（$ARGUMENTS または会話中の依頼）を、WBSync の既存Issueと同じ形式でGitHub Issueにする。

## 手順

1. **要望を整理する**
   - 1つのIssueは1つの変更単位にする。要望に独立した変更が複数含まれる場合は、Issueを分けて作成する
   - 対象画面・期待する挙動が読み取れないなど、曖昧で書けない点がある場合のみユーザーに質問する

2. **関連ドキュメントを特定する**
   - `doc/index.md` を起点に、`doc/screens/`・`doc/requirements/`・`doc/tables/` から関連するファイルを探す
   - 現在の仕様を読み、変更内容が既存仕様のどこに影響するかを把握する

3. **重複を確認する**
   - `gh issue list --state open --search "<キーワード>"` で類似のオープンIssueがないか確認する
   - 重複・包含関係がありそうな場合は、作成前にユーザーへ伝えて判断を仰ぐ

4. **本文を作成する**（下記テンプレート）
   - 本文は一時ファイル（スクラッチパッド等、リポジトリ外）に書き出す

5. **Issueを作成する**
   - `gh issue create --title "<タイトル>" --body-file <一時ファイル>`
   - バグ修正なら `--label bug`、機能追加・改善なら `--label enhancement` を付ける
   - 作成後、Issue番号とURLを報告する

## タイトル

`<画面名・機能名>：<変更内容の要約>` の形式（全角コロン）。

例:
- `ダッシュボード：予定工数なしのタスクを遅れ集計から除外`
- `工数管理：実績・残工数・前倒し/遅れ列の見切れを解消（列幅調整）`

## 本文テンプレート

```markdown
## 概要
<何を・なぜ変えるのかを1〜3文で>

## 変更内容
- <実装者が行う具体的な変更を箇条書き>

## 受け入れ条件
- [ ] <人間がアプリを操作して確認する手順と期待結果>

## 関連ドキュメント
- doc/screens/xxx.md
- doc/requirements/xxx.md
```

### 受け入れ条件の書き方

- **人間がアプリを起動して目視・操作で確認する項目**として書く（「〇〇画面で△△すると、□□が表示される」）
- 内部実装ではなく、画面上で観察できる結果で書く
- 正常系に加え、要望から読み取れる境界・例外ケース（値が未設定、0件、親タスクなど）があれば含める
- 項目は確認しやすい粒度で2〜5個程度
